# One Day 服务器部署文档

本文以 Ubuntu 服务器、Nginx、systemd 和独立域名 `todo.example.com` 为例。把示例域名、仓库地址和证书路径换成自己的值。应用由同一个 Node 进程提供页面和 `/api`；`dist/` 和 `dist-server/` 必须一起部署。

## 部署前准备

- 域名已解析到服务器，服务器的 80、443 端口可访问。
- 安装 Node.js `>=24.14.0 <25`、Git、Nginx；使用 Corepack 启用项目指定的 pnpm `11.16.0`。确认 `node --version`、`corepack --version` 和 `command -v node`。下文 systemd 文件中的 Node 路径以 `command -v node` 的实际输出为准。
- 准备 HTTPS 证书。可使用服务器现有证书，或通过 Certbot 为 Nginx 申请并配置证书。证书签发和自动续期应在上线前确认。
- 为应用保留持久磁盘空间。账号和任务数据存在 SQLite 数据库，不要将 `/var/lib/one-day` 放在临时目录，也不要把它提交到 Git。

以下命令示例假定部署用户有 `sudo` 权限，应用文件位于 `/opt/one-day`，服务以专用用户 `one-day` 运行。首次部署时先把代码放到服务器：

```bash
sudo useradd --system --home /opt/one-day --shell /usr/sbin/nologin one-day
sudo git clone <仓库地址> /opt/one-day
sudo chown -R one-day:one-day /opt/one-day
sudo install -d -o one-day -g one-day -m 700 /var/lib/one-day
sudo install -d -m 700 /etc/one-day
cd /opt/one-day
corepack enable
corepack prepare pnpm@11.16.0 --activate
sudo -u one-day pnpm install --frozen-lockfile
sudo -u one-day pnpm build
```

若 `pnpm` 只安装在当前用户的版本管理器目录中，先为服务用户配置可执行的 Node/Corepack/pnpm 路径；不要把示例命令中的路径照搬到不同环境。部署机器也可以只接收在相同 Node 主版本下构建的 `dist/` 与 `dist-server/`，此时无需在服务器安装构建依赖，但仍需 Node 运行时。

## 配置服务

创建 `/etc/one-day/one-day.env`，内容如下；`ONE_DAY_ORIGIN` 必须与浏览器地址栏中的来源完全一致，包括协议、域名和非默认端口。不要在末尾加 `/` 或路径。

```ini
ONE_DAY_ORIGIN=https://todo.example.com
ONE_DAY_DATABASE=/var/lib/one-day/one-day.sqlite
HOST=127.0.0.1
PORT=53028
NODE_ENV=production
```

```bash
sudo chmod 600 /etc/one-day/one-day.env
```

创建 `/etc/systemd/system/one-day.service`。将 `ExecStart` 中的 `/usr/bin/node` 改为前面 `command -v node` 得到的绝对路径。

```ini
[Unit]
Description=One Day web application
After=network.target

[Service]
Type=simple
User=one-day
Group=one-day
WorkingDirectory=/opt/one-day
EnvironmentFile=/etc/one-day/one-day.env
ExecStart=/usr/bin/node /opt/one-day/dist-server/main.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now one-day
sudo systemctl status one-day
```

程序默认只监听 `127.0.0.1:53028`。不要把该端口直接暴露到公网；外部访问统一走 HTTPS 反向代理。若启动失败，查看 `sudo journalctl -u one-day -n 100 --no-pager`，重点检查 Node 路径、环境文件、`dist/` 和数据库目录权限。

## 配置 Nginx 与 HTTPS

下面是站点配置的核心内容。证书路径替换成服务器上真实存在的文件；若使用 Certbot，可先按其文档申请证书并由它管理 HTTPS 配置。代理应把所有路径（包括 `/api`）转发给 Node，避免由 Nginx 单独服务旧版本静态文件。

```nginx
server {
    listen 80;
    server_name todo.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name todo.example.com;

    ssl_certificate     /etc/letsencrypt/live/todo.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/todo.example.com/privkey.pem;

    client_max_body_size 6m;

    location / {
        proxy_pass http://127.0.0.1:53028;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

将配置保存到 Nginx 的站点目录并启用，随后执行 `sudo nginx -t` 和 `sudo systemctl reload nginx`。应用的 POST 接口严格核对浏览器 `Origin` 与 `ONE_DAY_ORIGIN`；域名、协议或端口不一致时，注册、登录和保存会返回 403。`client_max_body_size` 留有余量，但应用本身仍限制 JSON 请求为 5 MiB。

## 上线检查

1. 在服务器上运行 `curl -I http://127.0.0.1:53028/`，应返回页面响应；浏览器访问 `https://todo.example.com`，确认没有证书警告。
2. 打开 `https://todo.example.com/api/session`，未登录时应返回 401。随后通过页面注册测试账号、登录、创建任务，并刷新页面确认数据仍在。
3. 在浏览器开发者工具中确认会话 Cookie 包含 `HttpOnly`、`Secure` 和 `SameSite=Strict`；再用另一台设备登录，检查任务同步。
4. 重启服务 `sudo systemctl restart one-day`，确认任务仍在；检查 `sudo systemctl status one-day` 和 `sudo journalctl -u one-day -n 100 --no-pager`。
5. 按[发布检查清单](release-checklist.md)在目标 Android/iOS 真机上检查安装、离线外壳和升级流程。离线时不能编辑账号数据，关闭应用后也不能保证提醒准时送达。

## 更新与回滚

每次更新前备份数据库，保留当前可运行的代码版本或 Git 提交号。单机部署的更新流程：

```bash
sudo systemctl stop one-day
sudo tar -C /var/lib -czf /root/one-day-data-$(date +%Y%m%d-%H%M%S).tar.gz one-day
cd /opt/one-day
sudo -u one-day git pull --ff-only
sudo -u one-day pnpm install --frozen-lockfile
sudo -u one-day pnpm build
sudo systemctl start one-day
sudo systemctl status one-day
```

备份时先停服务，因为 SQLite 使用 WAL 模式，运行时可能同时存在 `.sqlite`、`.sqlite-wal` 和 `.sqlite-shm`。不要只复制主 `.sqlite` 文件。若构建失败，先不要启动不完整的新版本；恢复到先前提交并重新安装、构建。若新版本已写入数据库，回滚代码前应评估数据格式兼容性，必要时连同停机前备份一起恢复。

恢复数据库时先停服务，将备份解压回 `/var/lib/one-day`，确认目录和文件属主为 `one-day`、权限只允许服务用户访问，再启动服务。恢复会覆盖备份之后的账号和任务变更；先另存当前数据，并在维护窗口操作。定期把备份复制到服务器以外的安全位置，并实际演练恢复。

## 注意事项

- `ONE_DAY_ORIGIN` 是站点来源，不是服务监听地址；HTTPS 由 Nginx 终止，Node 仍可监听本机 HTTP。
- 旧版浏览器本地数据受同源限制。更换协议、域名或端口时，用户需从旧站点导出 JSON，再在新站点导入。
- 当前服务使用单个 SQLite 文件与进程内登录限流，不要把多个应用实例指向同一数据库并当作已支持的集群部署。
